# FM 애플리케이션 설계 고려 사항

## 이 문서에서 배울 것

파운데이션 모델(FM)을 애플리케이션에 적용할 때는 “가장 유명한 모델”이 아니라 업무 요구에 맞는 모델과 구조를 선택해야 합니다. 이 문서에서는 모델 선택 기준과 추론 파라미터, RAG와 벡터 저장소, FM 사용자 지정 방식의 비용 절충, AI 에이전트의 역할을 연결합니다.

## 선수 지식과 한 줄 요약

- 선수 지식: D2의 FM·토큰·임베딩·벡터·RAG·에이전트 개념이 필요합니다.
- 한 줄 요약: **모델 선택은 품질 하나의 문제가 아니라 작업·데이터·지연 시간·비용·보안·운영을 함께 맞추는 설계 문제입니다.**

## 모델 선택 기준

### 작업과 모달리티

먼저 애플리케이션이 무엇을 해야 하는지 정의합니다. 문서 요약인지, 질문 응답인지, 이미지 생성인지, 음성 처리인지, 코드 생성인지에 따라 필요한 모델의 모달리티와 능력이 달라집니다.

- 텍스트 입력·텍스트 출력: 요약, 분류 보조, 질의응답, 초안 작성
- 텍스트 입력·이미지 출력: 이미지 생성
- 이미지 입력·텍스트 출력: 이미지 설명, 문서·차트 이해
- 텍스트·이미지·오디오 등 복합 입력: 멀티모달 업무

### 품질과 모델 크기·복잡도

더 큰 모델은 복잡한 지시나 다양한 표현을 처리하는 데 유리할 수 있지만, 모델 복잡도와 함께 비용·지연 시간·운영 부담이 증가할 수 있습니다. 반대로 작은 모델은 간단한 분류나 짧은 응답에서 빠르고 경제적일 수 있지만 복잡한 추론이나 긴 컨텍스트에는 부족할 수 있습니다.

“큰 모델이 항상 최선”이 아니라 실제 업무 질문으로 품질·지연 시간·비용을 비교합니다.

### 다국어와 도메인 적합성

사용자가 사용하는 언어, 문체, 전문 용어를 모델이 충분히 처리하는지 확인합니다. 다국어 지원이 있다고 해서 모든 언어에서 품질이 같은 것은 아닙니다. 실제 사용자 질문과 도메인 자료로 평가합니다.

### 입력·출력 길이

입력 길이는 프롬프트·검색 결과·대화 기록이 모델 컨텍스트에 들어갈 수 있는 정도와 관련됩니다. 출력 길이는 모델이 생성할 수 있는 답변의 최대 범위와 비용·지연 시간에 영향을 줍니다.

긴 입력을 무조건 모두 넣으면 다음 문제가 생길 수 있습니다.

- 입력 토큰 비용 증가
- 응답 지연 시간 증가
- 중요한 정보와 관계없는 정보가 섞임
- 컨텍스트 한도 초과 또는 일부 정보 손실

필요한 자료만 검색·요약·정리해 제공하는 것이 항상 더 좋은 설계는 아니지만, 먼저 검토할 기본 전략입니다.

### 사용자 지정 가능성과 운영 조건

모델을 프롬프트로 조정할 수 있는지, RAG로 업무 지식을 연결할 수 있는지, 미세 조정이나 지속적인 사전 훈련이 가능한지 확인합니다. 사용자 지정이 가능하더라도 데이터 준비·평가·배포·업데이트를 운영할 팀이 있는지 함께 봅니다.

### 비용·지연 시간·프롬프트 캐싱

모델 호출 비용은 입력·출력 토큰, 모델, 모달리티와 가격 방식의 영향을 받을 수 있습니다. 응답 시간이 중요한 대화형 애플리케이션에서는 모델 크기·입출력 길이·검색·도구 호출도 함께 측정합니다.

[Amazon Bedrock의 프롬프트 캐싱](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)은 지원되는 모델과 API에서 반복되는 프롬프트 컨텍스트를 재사용해 입력 처리 비용과 추론 지연 시간을 줄이는 데 활용할 수 있습니다. 긴 문서나 고정된 지시가 여러 요청에서 반복되는 경우 검토합니다.

프롬프트 캐싱은 모든 모델·API에서 같은 방식으로 지원되는 기능이 아니며, 캐시 적중이 항상 보장되는 것도 아닙니다. 동적인 부분과 재사용할 정적인 부분을 구분하고 최신 공식 지원 범위를 확인합니다.

## 추론 파라미터가 응답에 미치는 영향

### 온도(temperature)

온도는 모델이 다음 토큰을 선택할 때 출력의 다양성과 무작위성에 영향을 주는 추론 파라미터입니다.

- 낮은 온도: 더 일관되고 예측 가능한 표현을 기대할 수 있음
- 높은 온도: 다양한 표현과 창의적인 결과를 기대할 수 있음

온도를 낮춘다고 사실성이 자동으로 보장되거나 환각이 사라지는 것은 아닙니다. 사실 확인, 근거 제공, 검색, 출력 검증은 별도로 설계해야 합니다.

### 입력·출력 길이

입력이 너무 짧으면 필요한 업무 맥락이 빠지고, 너무 길면 비용과 지연이 늘거나 중요한 정보가 묻힐 수 있습니다. 출력 길이를 너무 짧게 제한하면 답변이 잘릴 수 있고, 너무 길게 허용하면 불필요한 내용과 비용이 늘 수 있습니다.

따라서 파라미터는 “무조건 최대”가 아니라 업무의 응답 형식과 품질 기준에 맞춰 평가 데이터로 조정합니다.

## RAG와 Amazon Bedrock Knowledge Bases

### RAG란 무엇인가요?

검색 증강 생성(Retrieval-Augmented Generation, RAG)은 사용자의 질문과 관련된 외부 자료를 검색한 뒤, 검색 결과를 모델의 컨텍스트로 제공해 답변을 생성하는 방식입니다.

```text
업무 문서 → 조각화·임베딩 → 벡터 저장소
                                ↑
사용자 질문 → 질문 임베딩 → 관련 자료 검색
                                ↓
                    질문 + 검색 컨텍스트 → FM → 답변
```

RAG는 모델을 다시 훈련하지 않고도 최신 정책·제품 정보·사내 문서를 답변에 활용할 수 있게 합니다. 다만 검색 결과가 틀리거나 오래되었거나 권한이 없는 자료라면 답변 품질도 나빠질 수 있습니다.

### RAG의 비즈니스 적용

- 사내 정책·매뉴얼 기반 직원 질의응답
- 제품 설명·지원 문서 기반 고객 상담 보조
- 계약·보고서·연구 자료 검색과 요약
- 최신 재고·가격·업무 규칙을 조회하는 애플리케이션

고위험 업무에서는 검색된 출처를 표시하고, 사용자의 접근 권한을 검색 단계에서 확인하며, 사람이 최종 답변을 검토할 수 있게 합니다.

### Amazon Bedrock Knowledge Bases

[Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html)는 데이터 소스에서 관련 정보를 검색해 생성형 AI 애플리케이션의 답변을 보완하는 관리형 RAG 경로입니다. 문서 수집·조각화·임베딩·벡터 저장·검색의 일부 또는 전체를 관리형 구성으로 사용할 수 있습니다.

Knowledge Bases를 선택할 때도 다음을 확인합니다.

- 데이터 소스와 동기화 주기
- 청킹·임베딩·검색·재순위 지정 방식
- 문서별 접근 권한과 데이터 레지던시
- 답변에 출처를 포함할 필요성
- 검색 결과가 부족할 때의 대체 응답과 사람 전달
- 관리형 구성을 사용할지 직접 RAG 파이프라인을 운영할지

RAG는 모델의 가중치를 바꾸는 훈련이 아닙니다. 외부 자료를 추론 시점의 컨텍스트로 제공하는 애플리케이션 설계입니다.

## 임베딩과 벡터 저장소 선택

임베딩은 문서·질문을 의미를 반영한 숫자 벡터로 표현한 결과입니다. 벡터 저장소는 이 벡터와 원문·메타데이터를 저장하고, 질문과 가까운 벡터를 찾아 관련 자료를 반환합니다.

### AWS 서비스 비교

| 서비스 | 중심 강점 | 검토할 상황 | 주의할 점 |
|---|---|---|---|
| Amazon OpenSearch Service | 검색과 k-NN 벡터 검색 | 대규모 검색·필터·벡터 검색을 함께 운영할 때 | 인덱스·메모리·검색 성능과 운영 비용을 계획 |
| Amazon Aurora | 관계형 데이터베이스와 벡터 기능의 결합 | 기존 Aurora PostgreSQL 데이터와 벡터 검색을 함께 다룰 때 | 데이터베이스 용량·버전·pgvector와 연결 방식 확인 |
| Amazon RDS for PostgreSQL | 관리형 PostgreSQL과 pgvector 활용 | 기존 PostgreSQL 관계형 데이터와 임베딩을 함께 관리할 때 | 데이터 규모·검색 성능·운영 구성을 평가 |
| Amazon Neptune | 연결 관계와 지식 그래프 | 사람·제품·문서·조직처럼 관계 자체가 중요한 지식 그래프 | 단순 벡터 저장소가 아니라 그래프 질의 요구를 먼저 확인 |
| Amazon Bedrock Knowledge Bases | 관리형 RAG 구성 | 직접 수집·임베딩·검색 파이프라인을 줄이고 빠르게 시작할 때 | 지원 기능·저장소·리전·권한·비용을 최신 문서에서 확인 |

[Amazon OpenSearch Service의 k-NN 검색](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/knn.html)은 벡터 공간에서 가까운 항목을 찾는 검색 기능을 제공합니다. [Amazon Aurora PostgreSQL을 Bedrock Knowledge Base로 사용하는 방법](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.VectorDB.html)은 관계형 PostgreSQL 환경에 문서 조각과 벡터를 저장하는 예를 보여 줍니다. [Amazon Neptune](https://docs.aws.amazon.com/neptune/latest/userguide/intro.html)은 고도로 연결된 데이터를 위한 그래프 데이터베이스이므로, 지식 그래프·관계 탐색이 핵심인 문제에서 검토합니다.

시험에서는 “벡터를 저장할 수 있다”는 공통점만 보지 말고, **검색 중심인지, 기존 관계형 데이터 중심인지, 그래프 관계 중심인지, 관리형 RAG 단순화가 필요한지**를 판단합니다.

## FM 사용자 지정 방식과 비용 절충

| 접근 방식 | 무엇을 바꾸나요? | 장점 | 비용·부담 |
|---|---|---|---|
| 컨텍스트 내 학습 | 예시를 프롬프트에 넣음 | 가장 빠르게 실험 가능 | 요청마다 예시 토큰 비용·컨텍스트 길이 증가 |
| RAG | 외부 자료를 검색해 컨텍스트에 넣음 | 최신 업무 지식과 출처 연결 | 수집·임베딩·검색·저장·권한 설계 필요 |
| 미세 조정 | 업무 예시로 모델 파라미터를 조정 | 특정 형식·스타일·작업에 맞출 가능 | 데이터 준비·훈련·평가·배포 비용 발생 |
| 지속적인 사전 훈련 | 추가 도메인 데이터로 사전 학습을 이어감 | 특정 도메인 언어·지식 패턴을 넓게 반영 가능 | 큰 데이터·컴퓨팅·검증 부담 |
| 모델 증류 | 큰 교사 모델의 능력을 작은 모델로 전달 | 추론 비용·지연 시간 감소 가능 | 교사 생성·훈련·품질 손실 평가 필요 |
| 처음부터 사전 훈련 | 모델을 새로 만듦 | 가장 넓은 설계·데이터 통제 | 막대한 데이터·컴퓨팅·전문성·운영 비용 |

판단 순서는 보통 다음처럼 단순한 방법부터 비교합니다.

```text
프롬프트·컨텍스트 내 학습
          ↓ 부족하면
RAG 또는 도구 연결
          ↓ 형식·행동·스타일을 반복 학습해야 하면
미세 조정
          ↓ 대규모 도메인 지식·모델 자체가 필요하면
지속적인 사전 훈련·증류·재훈련 검토
```

이 순서는 절대 규칙이 아닙니다. 데이터 최신성이 핵심이면 RAG가 미세 조정보다 적합할 수 있고, 반복되는 출력 형식이 핵심이면 미세 조정을 검토할 수 있습니다. 비용뿐 아니라 업데이트 주기·품질·보안·운영 책임을 함께 봅니다.

## AI 에이전트의 역할과 비즈니스 애플리케이션

AI 에이전트는 사용자의 목표를 받아 모델의 추론, 도구 호출, 외부 시스템 조회, 결과 확인을 여러 단계로 조합합니다. 단순히 한 번 답하는 FM 호출과 달리, 다음 행동을 선택하고 작업 상태를 관리해야 합니다.

```text
목표
 ↓
상황 파악 → 계획·추론 → 도구 호출 → 결과 확인
                    ↑             ↓
                    └── 다음 행동 또는 완료
```

활용 사례는 다음과 같습니다.

- 주문 상태 조회 후 배송 시스템에 변경 요청
- 고객 문의를 분류하고 지식 베이스를 검색한 뒤 상담 티켓 초안 작성
- 여러 데이터 소스에서 정보를 모아 보고서 초안 작성
- 개발 작업에서 코드 저장소 검색·테스트 실행·결과 요약

에이전트는 강력하지만 도구 권한과 잘못된 행동의 위험이 커집니다. 도구별 최소 권한, 승인 단계, 호출 기록, 실패·재시도·중단 조건, 민감한 작업의 사람 검토를 설계합니다.

## 실무형 시나리오

한 기업이 직원에게 최신 인사 정책을 답변하고, 필요하면 휴가 신청까지 도와주는 애플리케이션을 만든다고 가정합니다.

1. 정책 답변은 Amazon Bedrock Knowledge Bases를 활용한 RAG로 최신 문서와 출처를 연결합니다.
2. 직원별로 볼 수 있는 정책이 다르므로 검색 단계에서 권한을 확인합니다.
3. 휴가 신청은 에이전트가 HR 시스템 도구를 호출하지만, 실제 제출 전 직원의 확인을 받습니다.
4. 짧은 FAQ는 작은 모델로 처리하고, 복잡한 정책 해석만 더 큰 모델로 보냅니다.
5. 모델 선택은 정확도뿐 아니라 지연 시간·호출 비용·다국어·출력 길이로 비교합니다.
6. 답변 정확도, 출처 포함률, 작업 완료율, 사람에게 넘겨진 비율, 상호 작용당 비용을 측정합니다.

이 구조는 모델 하나를 고르는 문제가 아니라 **검색·권한·도구·사람 승인·평가 지표를 함께 설계하는 문제**입니다.

## 시험에서 판단하는 단서

- “모델을 고르라” → 비용·모달리티·지연·다국어·크기·복잡도·사용자 지정·입출력 길이 비교
- “창의적이고 다양한 답변” → 온도 조정 검토
- “일관되고 형식이 정해진 답변” → 낮은 온도·출력 형식·검증을 함께 검토
- “최신 사내 문서로 답변” → RAG 또는 Amazon Bedrock Knowledge Bases
- “문서·질문을 숫자 벡터로 바꾸고 가까운 자료 검색” → 임베딩·벡터 저장소
- “관계형 데이터와 벡터를 함께 저장” → Aurora 또는 RDS for PostgreSQL 검토
- “고도로 연결된 관계·지식 그래프 탐색” → Amazon Neptune 검토
- “반복되는 긴 정적 컨텍스트” → 프롬프트 캐싱 검토
- “특정 형식·스타일을 많은 예시로 반복 학습” → 미세 조정 검토
- “여러 시스템을 조회하고 행동 수행” → AI 에이전트·도구 호출
- “호출 비용·지연 시간 절감” → 작은 모델·짧은 컨텍스트·캐싱·증류 등을 비교

## 자주 하는 오해

### 오해 1: RAG는 모델을 재훈련하는 방법이다

RAG는 추론 시점에 외부 자료를 검색해 컨텍스트로 제공하는 애플리케이션 방식입니다. 모델 파라미터를 바꾸는 미세 조정과 구분합니다.

### 오해 2: 벡터 데이터베이스는 모두 같은 역할이다

여러 서비스가 벡터를 저장하거나 검색할 수 있지만, 검색 기능·관계형 데이터·그래프 데이터·관리형 수준·운영 비용이 다릅니다. 업무의 데이터 구조와 검색 요구를 먼저 봅니다.

### 오해 3: 온도를 높이면 더 정확해진다

온도는 출력 다양성에 영향을 주는 파라미터입니다. 정확성·최신성·근거를 보장하지 않으며 검색·검증·평가가 별도로 필요합니다.

### 오해 4: 미세 조정이 최신 문서 문제를 해결한다

미세 조정 후에도 업무 문서가 바뀌면 모델을 다시 업데이트해야 합니다. 자주 변하는 지식은 RAG가 더 적합할 수 있습니다.

### 오해 5: 에이전트가 도구를 사용할 수 있으면 모든 작업을 자동 승인해도 된다

도구 호출은 권한과 부작용을 동반합니다. 최소 권한·승인·감사 로그·중단 조건과 사람 검토를 설계해야 합니다.

## 핵심 정리

- FM 선택은 작업·모달리티·품질·다국어·크기·복잡도·비용·지연 시간·입출력 길이를 함께 비교합니다.
- 온도는 출력의 다양성에 영향을 주지만 사실성을 보장하지 않습니다.
- RAG는 검색된 외부 자료를 추론 컨텍스트로 제공하며, 모델 재훈련과 다릅니다.
- Amazon Bedrock Knowledge Bases는 관리형 RAG 구성을 빠르게 시작하는 선택지입니다.
- OpenSearch Service는 검색·k-NN 벡터 검색, Aurora와 RDS for PostgreSQL은 관계형 데이터와 벡터 결합, Neptune은 연결 관계와 지식 그래프에 강점이 있습니다.
- 컨텍스트 내 학습·RAG·미세 조정·지속적인 사전 훈련·증류는 품질·최신성·비용·운영 부담이 서로 다릅니다.
- AI 에이전트는 모델과 도구·외부 시스템을 여러 단계로 조정하므로 권한·승인·관찰성이 필요합니다.

**한 문장 암기 포인트:** `최신 지식은 RAG`, `반복되는 형식·행동은 미세 조정`, `관계 탐색은 그래프`, `여러 시스템 행동은 에이전트`를 먼저 떠올립니다.
