# 프롬프트 엔지니어링·RAG·에이전트 프롬프트

## 이 문서에서 배울 것

프롬프트 엔지니어링은 모델이 원하는 작업을 더 잘 수행하도록 입력을 설계하고 반복해서 개선하는 과정입니다. 이 문서에서는 프롬프트의 구성 요소, zero-shot·one-shot·few-shot·생각의 사슬, 템플릿·출력 형식·가드레일, RAG와 에이전트의 프롬프트 구조, 프롬프트 공격 위험과 Amazon Bedrock Prompt Management를 설명합니다.

## 선수 지식과 한 줄 요약

- 선수 지식: D2의 토큰·컨텍스트·RAG·에이전트와 D3 3.1의 FM 애플리케이션 설계를 알고 있으면 좋습니다.
- 한 줄 요약: **좋은 프롬프트는 모델에게 목적·자료·제약·출력 형식을 명확히 알려 주고, 실제 예시로 평가·개선·버전 관리합니다.**

## 프롬프트 엔지니어링이란?

프롬프트 엔지니어링은 대규모 언어 모델(LLM)에 제공하는 입력을 설계·시험·개선하여 원하는 응답을 얻는 방법입니다. 모델을 다시 훈련하지 않고도 작업 지시, 말투, 출력 형식과 답변 범위를 조정할 수 있습니다.

프롬프트를 잘 작성해도 모델이 항상 정확하거나 안전한 답을 내는 것은 아닙니다. 프롬프트는 RAG·도구·가드레일·출력 검증·사람 검토와 함께 애플리케이션의 한 계층으로 사용합니다.

## 프롬프트의 구성 요소

### 명령과 목표

모델이 수행해야 할 작업을 동사로 분명하게 씁니다. “이 문서를 처리해 주세요”보다 “다음 정책 문서에서 자격 조건 세 가지를 요약하고, 근거 문단을 함께 표시하세요”가 판단 기준이 명확합니다.

### 컨텍스트

작업에 필요한 배경·자료·대상 독자·시간 범위를 제공합니다. RAG를 사용하는 경우 검색된 문서 조각이 컨텍스트가 될 수 있습니다. 컨텍스트는 많다고 항상 좋은 것이 아니며, 관련성·최신성·권한을 확인해야 합니다.

### 입력

요약·분류·변환할 실제 텍스트나 질문을 구분해 넣습니다. 사용자 입력과 개발자가 정한 지시를 분리하면 사용자가 입력에 새로운 지시를 섞어 시스템의 목표를 바꾸는 위험을 줄이는 데 도움이 됩니다.

### 제약과 가드레일

모델이 하지 말아야 할 일, 답변할 수 없는 범위, 개인정보 처리 규칙, 근거가 없을 때의 응답, 도구 호출 조건을 명시합니다. “모르는 내용은 추측하지 말고 근거 부족을 알리세요” 같은 규칙은 환각 위험을 줄이는 데 도움을 줄 수 있지만, 단독 보장은 아닙니다.

### 출력 형식

답변의 구조와 형식을 지정합니다. 예를 들어 제목·요약·근거·불확실성의 네 항목으로 답하거나, 분류 결과와 근거를 구분하도록 요구할 수 있습니다. 형식을 명확히 하면 후속 시스템이 결과를 처리하기도 쉬워집니다.

### 네거티브 프롬프트

네거티브 프롬프트는 생성 결과에서 피하고 싶은 요소를 지정하는 방식입니다. 이미지 생성에서는 “텍스트를 넣지 않음”, “흐린 배경을 피함”처럼 사용될 수 있고, 텍스트 작업에서는 금지할 주제·표현·형식을 설명할 수 있습니다.

네거티브 프롬프트만으로 안전성을 보장할 수 없습니다. 입력 검증, 출력 필터링, 권한 제어와 함께 사용합니다.

### 모델 잠재 공간

모델 잠재 공간(latent space)은 모델이 학습한 개념·패턴·관계가 수치적 표현으로 조직되어 있는 내부 표현을 설명할 때 사용하는 개념입니다. 프롬프트는 이 내부 표현에서 어떤 작업·개념·스타일과 관련된 출력을 유도합니다.

초보자는 잠재 공간을 모델 안의 “검색 가능한 문서 폴더”로 오해하면 안 됩니다. 모델 내부의 표현이 곧 최신 사실 데이터베이스나 출처 저장소를 의미하지는 않습니다.

## 프롬프트 기법

### Zero-shot

예시를 주지 않고 작업 지시만 제공합니다.

```text
다음 고객 문의를 배송 지연, 환불, 제품 문의 중 하나로 분류하세요.
답변은 범주 이름 하나만 출력하세요.
```

작업이 단순하고 지시가 명확할 때 빠르게 시작할 수 있습니다. 업무 표현이 복잡하거나 출력 형식이 어려우면 결과가 흔들릴 수 있습니다.

### One-shot

원하는 입력과 출력의 예시를 하나 제공합니다. 모델이 업무의 분류 기준이나 문체를 이해하는 데 도움을 줄 수 있습니다.

```text
예시:
문의: 주문한 상품이 아직 도착하지 않았습니다.
분류: 배송 지연

이제 다음 문의를 같은 기준으로 분류하세요.
```

예시 하나가 실제 업무를 대표하지 않으면 잘못된 기준을 학습한 것처럼 반응할 수 있으므로 예시의 품질을 확인합니다.

### Few-shot

여러 개의 입력·출력 예시를 제공합니다. 다양한 경계 사례와 원하는 형식을 보여 줄 수 있지만, 예시가 늘어나면 입력 토큰 비용과 컨텍스트 길이가 증가합니다.

예시는 무작위로 많이 넣기보다 실제 업무를 대표하고, 서로 모순되지 않으며, 민감한 정보를 포함하지 않도록 큐레이션합니다.

### 생각의 사슬(Chain-of-Thought)

복잡한 문제를 작은 추론 단계로 나누도록 유도하는 프롬프트 방식입니다. 단계별 점검이 도움이 되는 계산·분류·계획 문제에서 사용할 수 있습니다.

실무에서는 모델의 내부 추론을 무조건 그대로 사용자에게 노출하기보다, 필요한 경우 **간결한 근거·검증 결과·참조 출처**를 별도로 제공하도록 설계합니다. 생각의 사슬을 요청한다고 답변이 자동으로 정확해지는 것은 아닙니다.

### 프롬프트 템플릿

공통 지시와 변수 위치를 미리 정해 여러 요청에 재사용하는 형식입니다.

```text
역할: {대상_역할}
목표: {작업_목표}
컨텍스트:
{검색된_자료}
입력:
{사용자_질문}
제약: 근거가 없는 내용은 추측하지 말 것.
출력 형식: 요약 / 근거 / 불확실성
```

템플릿은 일관성을 높이고 실험을 쉽게 하지만, 변수에 악성 지시나 민감한 정보가 들어오지 않는지 검사해야 합니다.

## 좋은 프롬프트를 만드는 원칙

### 구체적이고 간결하게 작성

작업 대상, 원하는 결과, 독자, 제한 조건, 출력 형식을 명시합니다. 불필요하게 긴 설명을 덧붙이기보다 모델이 판단해야 하는 기준을 분명히 합니다.

### 예시와 출력 형식을 함께 사용

경계 사례를 포함한 예시와 원하는 출력 구조를 제공하면 결과를 비교하기 쉬워집니다. 다만 예시의 편향·오류·개인정보가 모델 응답에 영향을 줄 수 있습니다.

### 반복 실험

한 번의 성공 결과만 보고 프롬프트를 확정하지 않습니다. 대표적인 정상 사례, 애매한 사례, 실패가 중요한 사례, 악의적인 입력으로 테스트합니다.

비교할 때는 프롬프트만 바꾸고 모델·데이터·추론 파라미터를 가능한 한 일정하게 유지하면 원인을 파악하기 쉽습니다.

### 가드레일과 검증 연결

프롬프트에 금지 규칙을 적는 것만으로 충분하지 않습니다. 입력·출력 검증, 모델 안전성 기능, 민감 데이터 보호, 도구 권한, 사람 승인과 함께 방어 계층을 구성합니다.

### 발견과 관찰

사용자 질문과 실패 응답을 개인정보 정책에 맞게 분석해 어떤 지시가 부족한지 발견합니다. 프롬프트 버전, 모델, 추론 파라미터, 검색 결과와 평가 결과를 기록하면 개선이 재현 가능해집니다.

## RAG에서의 프롬프트

RAG 프롬프트는 질문과 검색된 컨텍스트를 명확히 구분해야 합니다.

```text
시스템 지시:
제공된 컨텍스트 안에서만 답하세요. 근거가 없으면 모른다고 말하세요.

검색된 컨텍스트:
--- 문서 A ---
{검색된_문서_조각}
--- 문서 끝 ---

사용자 질문:
{질문}

출력:
답변 / 근거 문서 / 확인이 필요한 부분
```

RAG 프롬프트를 설계할 때는 다음을 확인합니다.

- 검색된 문서가 질문과 실제로 관련 있는가
- 문서의 최신성과 사용자 권한이 확인되었는가
- 검색 자료 안의 지시를 무조건 시스템 지시로 취급하지 않는가
- 출처와 인용을 답변에 포함할 수 있는가
- 자료가 부족할 때 추측 대신 한계를 알리는가

검색 문서 안에 “이전 지시를 무시하라”는 문장이 있어도 그것은 데이터일 수 있습니다. 검색된 자료와 애플리케이션 지시를 분리하고, 문서 내용을 실행 지시로 자동 승격하지 않습니다.

## 에이전트에서의 프롬프트

에이전트 프롬프트는 단순 답변보다 많은 조건을 포함합니다.

- 에이전트의 역할과 달성할 목표
- 사용할 수 있는 도구와 각 도구의 목적
- 도구 입력 형식과 허용 범위
- 도구를 호출하기 전 확인해야 할 조건
- 실패·재시도·중단 조건
- 민감한 작업에서 사람 승인을 요구하는 조건
- 결과를 사용자에게 요약하는 방식

에이전트가 “환불 처리”라는 목표를 받더라도 환불 API를 바로 호출하게 하지 않습니다. 주문 상태·환불 자격·금액·사용자 확인을 검증하고, 실제 부작용이 있는 호출 전 승인 단계를 둡니다.

## 프롬프트 위험과 한계

### 프롬프트 노출 또는 유출

공격자가 시스템 프롬프트·개발자 지시·비공개 설정을 출력하도록 유도하는 공격입니다. 시스템 프롬프트에 비밀 키나 개인정보를 넣지 않고, 프롬프트가 보안 경계가 되지 않도록 권한을 별도로 관리합니다.

### 데이터 중독

훈련 데이터·예시·검색 문서·피드백에 악성 또는 잘못된 내용을 섞어 모델이나 RAG 결과의 행동을 왜곡하는 위험입니다. 데이터 출처·무결성·검토·버전을 관리합니다.

### Prompt injection

사용자 입력이나 검색 문서가 개발자 지시를 무시하거나 목표를 바꾸도록 모델에 명령하는 애플리케이션 수준 공격입니다. 직접 사용자 입력에서 발생할 수도 있고, 악성 문서가 검색 결과로 들어오는 간접 공격일 수도 있습니다.

### 하이재킹(goal hijacking)

공격자가 애플리케이션의 원래 목표를 다른 목표로 바꾸거나, 에이전트가 공격자가 원하는 도구를 호출하게 만드는 상황입니다. 에이전트 권한·도구 목록·행동 범위를 제한합니다.

### 탈옥(jailbreak)

모델의 안전성·사용 정책을 우회해 원래 거부해야 하는 출력이나 행동을 유도하는 공격입니다. 역할극·압박·여러 단계 지시 등 다양한 형태로 나타날 수 있습니다.

### 대응 계층

AWS 공식 자료에서도 prompt injection을 애플리케이션 수준의 보안 문제로 설명합니다. 다음을 함께 적용합니다.

1. 사용자 입력과 시스템·개발자 지시를 분리하고 검증·정제합니다.
2. 프롬프트에 비밀·장기 자격 증명·불필요한 개인정보를 넣지 않습니다.
3. 도구는 최소 권한과 허용 목록으로 제한합니다.
4. 입력 공격과 출력 위험을 Guardrails·필터·정책으로 검사합니다.
5. 결과 형식·권한·업무 규칙을 애플리케이션에서 다시 검증합니다.
6. 환불·삭제·전송 같은 부작용 작업은 사람 승인이나 추가 확인을 요구합니다.
7. 정상·경계·공격 입력으로 정기적인 보안 평가를 수행합니다.

방어 규칙을 프롬프트에만 숨겨 두면 충분하지 않습니다. 권한 부여와 검증은 모델 밖의 애플리케이션 계층에서도 수행해야 합니다.

## Amazon Bedrock Prompt Management

[Amazon Bedrock Prompt Management](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management.html)은 재사용할 프롬프트를 만들고, 수정하고, 저장하고, 변수와 모델·추론 설정을 관리하는 기능입니다. 프롬프트 변형을 비교하고 버전을 저장해 애플리케이션에 사용할 버전을 선택할 수 있습니다.

### 운영 전략

| 단계 | 확인할 일 |
|---|---|
| 초안 | 목적·입력·출력 형식·금지 범위·변수를 정의 |
| 실험 | 대표 데이터·경계 사례·공격 입력으로 변형 비교 |
| 검토 | 품질·안전·비용·지연·편향·출처 요구를 확인 |
| 버전 등록 | 변경 내용·사용 모델·파라미터·평가 결과를 기록 |
| 배포 | 검토된 버전을 애플리케이션·Flow·에이전트에 연결 |
| 모니터링 | 실패·사용자 피드백·비용·모델 변경을 관찰 |
| 롤백 | 품질이나 안전 문제가 생기면 이전 버전으로 되돌림 |

Prompt Management는 좋은 프롬프트를 자동으로 보장하는 기능이 아닙니다. 버전 관리와 비교 실험을 쉽게 해 주는 운영 도구입니다.

## 실무형 시나리오

고객지원 에이전트가 사내 정책을 검색하고 답변 초안을 작성한다고 가정합니다.

1. 시스템 프롬프트에 역할·답변 범위·근거 없는 추측 금지를 정의합니다.
2. 사용자의 질문과 RAG 검색 문서를 별도 구역으로 표시합니다.
3. 검색 문서는 답변 근거로만 사용하고, 문서 속 지시를 실행 명령으로 취급하지 않도록 합니다.
4. 답변은 `요약 / 근거 / 불확실성 / 다음 단계` 형식으로 고정합니다.
5. 환불이나 계정 변경 도구를 호출할 때는 자격 검증과 고객 확인을 요구합니다.
6. Prompt Management에서 한국어 표현, 짧은 표현, 출처 강조 변형을 비교합니다.
7. 정상 질문뿐 아니라 “이전 지시를 무시하라” 같은 공격 입력으로 평가하고 승인된 버전을 배포합니다.

## 시험에서 판단하는 단서

- “모델에 작업·배경·출력 형식을 명확히 전달” → 프롬프트 구성·구체성
- “예시 없이 작업 지시만 제공” → zero-shot
- “예시 하나 제공” → one-shot
- “여러 입력·출력 예시 제공” → few-shot
- “복잡한 문제를 단계로 나눔” → 생각의 사슬
- “여러 요청에서 같은 구조 재사용” → 프롬프트 템플릿
- “이미지에서 피할 요소 지정” → 네거티브 프롬프트
- “검색 문서가 시스템 지시를 덮어씀” → 간접 prompt injection 또는 데이터 중독 위험
- “시스템 프롬프트를 보여 달라는 요청” → 프롬프트 노출·유출
- “안전성 정책을 우회” → jailbreak·탈옥
- “에이전트의 원래 업무 목표가 공격자의 작업으로 바뀜” → 하이재킹
- “프롬프트를 저장·변형 비교·버전 관리” → Amazon Bedrock Prompt Management

## 자주 하는 오해

### 오해 1: 프롬프트가 명확하면 항상 정확한 답이 나온다

명확한 지시는 품질을 개선할 수 있지만, 모델의 지식 한계·환각·최신성·데이터 품질 문제를 없애지는 못합니다.

### 오해 2: few-shot 예시를 많이 넣을수록 무조건 좋다

예시가 늘면 비용과 컨텍스트 길이가 증가하고, 잘못되거나 편향된 예시가 결과를 악화시킬 수 있습니다. 대표적이고 일관된 예시를 선택합니다.

### 오해 3: 시스템 프롬프트에 비밀을 넣으면 사용자가 볼 수 없다

모델과 상호 작용하는 사용자가 프롬프트 추출을 시도할 수 있습니다. 비밀과 권한은 프롬프트가 아니라 보안 시스템으로 보호합니다.

### 오해 4: RAG 문서의 모든 문장은 믿을 수 있는 지시다

RAG 문서는 답변 자료일 수 있지만 악성 또는 오래된 내용을 포함할 수 있습니다. 데이터와 지시를 분리하고 출처·권한·무결성을 검증합니다.

### 오해 5: Prompt Management가 프롬프트 보안을 자동으로 해결한다

Prompt Management는 재사용·변형·버전 운영을 돕습니다. 입력 검증, Guardrails, IAM, 도구 권한, 출력 검증은 별도로 필요합니다.

## 핵심 정리

- 프롬프트에는 명령·컨텍스트·입력·제약·출력 형식이 들어갈 수 있습니다.
- zero-shot·one-shot·few-shot은 제공하는 예시 수의 차이입니다.
- 생각의 사슬은 복잡한 작업을 단계적으로 처리하도록 유도하지만 정확성·안전성을 보장하지 않습니다.
- RAG 검색 자료와 시스템 지시를 분리하고, 검색 문서의 내용을 자동 실행 명령으로 취급하지 않습니다.
- 에이전트 프롬프트에는 도구·권한·승인·실패·중단 조건이 포함되어야 합니다.
- 프롬프트 노출·데이터 중독·prompt injection·하이재킹·탈옥을 구분합니다.
- Amazon Bedrock Prompt Management는 프롬프트 재사용·변형 비교·버전 관리·배포 연결을 돕습니다.

**한 문장 암기 포인트:** `명확한 지시 + 검증 가능한 컨텍스트 + 제한된 도구 + 버전 평가`가 안전한 프롬프트 운영의 기본입니다.
