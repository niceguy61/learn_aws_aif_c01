# FM 성능 평가와 비즈니스 지표

## 이 문서에서 배울 것

FM 평가는 “답변이 자연스러운가?”만 확인하는 일이 아닙니다. 이 문서에서는 인간 평가·벤치마크 데이터세트·Amazon Bedrock 모델 평가를 비교하고, ROUGE·BLEU·BERTScore·LLM-as-a-judge의 의미와 한계를 설명합니다. 또한 RAG·에이전트·워크플로 애플리케이션의 품질과 생산성·참여·작업 완료율·만족도·상호 작용당 비용을 연결합니다.

## 선수 지식과 한 줄 요약

- 선수 지식: D1의 모델 지표·비즈니스 지표, D2의 GenAI 한계, D3의 RAG·에이전트 개념이 필요합니다.
- 한 줄 요약: **좋은 평가란 모델 점수를 높이는 것이 아니라 실제 사용자의 업무 목표와 안전 기준을 측정하는 것입니다.**

## FM 평가를 설계하는 순서

### 1. 평가 목적 정의

먼저 무엇을 비교하거나 개선하려는지 정합니다.

- 두 FM 중 어떤 모델이 업무에 더 적합한가
- 프롬프트 변경 전후 품질이 좋아졌는가
- 미세 조정 모델이 기본 모델보다 나은가
- RAG가 관련 문서를 제대로 찾고 근거 있는 답변을 만드는가
- 에이전트가 도구를 올바르게 사용하고 작업을 완료하는가

### 2. 대표 평가 데이터세트 구성

실제 사용자 질문을 개인정보 정책에 맞게 정제하고, 정상·경계·실패가 중요한·공격적인 사례를 포함합니다. 정답 또는 기대 기준이 필요한 경우 사람이 검토해 기준을 만듭니다.

평가 데이터는 모델이 훈련에 사용하지 않은 사례를 포함해야 합니다. 한 번 본 예시만으로 좋은 점수가 나오는지, 새로운 질문에도 일반화되는지 구분합니다.

### 3. 측정 기준과 임계값 결정

품질·안전·지연·비용·업무 성과의 허용 범위를 정합니다. 하나의 점수로 모든 목표를 표현하기보다, 어떤 조건을 반드시 만족해야 하는지와 어떤 항목을 절충할 수 있는지를 구분합니다.

### 4. 여러 방법으로 반복 평가

자동 지표·인간 평가·LLM 평가·실제 업무 지표를 함께 보고, 데이터·프롬프트·모델·파라미터·애플리케이션 버전을 기록합니다. 한 번의 평균 점수만으로 배포를 결정하지 않습니다.

## 평가 접근 방식

### 인간 평가

사람이 모델의 답변을 직접 읽고 정확성·관련성·도움 정도·안전성·문체 등을 평가합니다. 사람은 미묘한 의미와 업무 맥락을 판단할 수 있지만 비용·시간·평가자 간 기준 차이가 발생할 수 있습니다.

평가 지침에 점수 기준과 예시를 포함하고, 일부 답변은 여러 평가자가 검토해 일관성을 확인합니다. 고위험 업무에서는 자동 점수보다 전문가 평가와 승인 절차가 중요할 수 있습니다.

Amazon Bedrock의 인간 평가 작업은 선택한 모델의 응답을 사람 작업자가 평가·비교하는 방식으로 활용할 수 있습니다. 실제 지원 모델·리전·작업 조건은 최신 공식 문서에서 확인합니다.

### 벤치마크 데이터세트

벤치마크는 일정한 데이터와 과제로 여러 모델을 비교하는 기준입니다. 빠른 비교에 유용하지만, 공개 벤치마크 점수가 실제 회사의 언어·업무·사용자·안전 요구를 그대로 대표하지 않을 수 있습니다.

공개 벤치마크와 함께 자체 업무 데이터세트를 사용합니다. 시험에서는 “일반 벤치마크 점수가 높다”와 “특정 비즈니스 문제를 잘 해결한다”를 구분합니다.

### Amazon Bedrock 모델 평가

[Amazon Bedrock 모델 평가](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html)는 모델 또는 생성형 AI 리소스의 성능을 평가하는 관리형 작업을 제공하는 경로입니다. 평가 유형에 따라 자동 지표, 인간 작업자, LLM을 평가자로 사용하는 방식 등을 검토할 수 있습니다.

관리형 평가를 사용하더라도 평가 데이터의 대표성·민감 정보·평가 기준·결과 해석은 팀이 책임져야 합니다.

### LLM-as-a-judge

LLM-as-a-judge는 별도의 평가자 모델이 생성 모델의 응답을 기준에 따라 점수화·설명하도록 하는 방법입니다. 많은 응답을 비교하는 데 효율적일 수 있지만, 평가자 모델의 편향·기준 이해·표현 선호가 결과에 영향을 줄 수 있습니다.

평가자 점수만 정답으로 취급하지 않습니다. 사람 평가와 샘플 교차 검토를 통해 평가자 모델이 업무 기준과 맞는지 확인합니다.

## 텍스트 생성 품질 지표

### ROUGE

ROUGE(Recall-Oriented Understudy for Gisting Evaluation)는 생성 요약과 참조 요약 사이의 겹치는 단어·구문을 비교해 요약 품질을 평가하는 계열의 지표입니다. 참조 답변과 표현이 다르지만 의미가 같은 답변을 낮게 평가할 수 있습니다.

### BLEU

BLEU(Bilingual Evaluation Understudy)는 생성된 텍스트와 참조 텍스트 사이의 n-그램 겹침을 바탕으로 번역 등 생성 결과를 비교하는 지표입니다. 단어 표현의 일치에는 유용하지만 문맥·사실성·업무 유용성을 모두 설명하지는 못합니다.

### BERTScore

BERTScore는 임베딩 기반 표현을 사용해 생성 문장과 참조 문장의 의미적 유사성을 평가하는 방식입니다. 표면적인 단어가 달라도 의미가 비슷한 답변을 포착하는 데 도움을 줄 수 있지만, 의미가 비슷해 보이는 부정확한 답변을 자동으로 찾아내는 만능 지표는 아닙니다.

### 지표를 해석하는 방법

ROUGE·BLEU·BERTScore는 특정 품질 측면을 측정하는 도구입니다. 점수가 높다고 사실성·안전성·최신성·업무 성공이 자동으로 보장되지 않습니다. 업무 기준에 맞는 인간 평가와 비즈니스 지표를 추가합니다.

## 애플리케이션별 평가

### RAG 평가

RAG는 검색 단계와 생성 단계를 나누어 평가합니다.

| 평가 영역 | 확인 질문 |
|---|---|
| 검색 관련성 | 질문에 적합한 문서를 찾았나요? |
| 검색 완전성 | 답변에 필요한 핵심 자료를 놓치지 않았나요? |
| 최신성·권한 | 최신 문서이며 사용자가 볼 권한이 있는 자료인가요? |
| 근거성 | 답변이 검색된 자료에 근거하나요? |
| 답변 품질 | 질문에 직접 답하고 사실 오류가 적나요? |
| 출처 | 사용자가 원문을 확인할 수 있나요? |

검색이 실패했는데 생성 모델만 평가하면 원인을 알 수 없습니다. 검색 결과와 최종 답변을 각각 기록합니다.

### 에이전트 평가

에이전트는 최종 문장뿐 아니라 행동 과정을 평가합니다.

- 목표를 올바르게 이해했는가
- 적절한 도구를 선택했는가
- 도구 입력이 정확하고 권한 범위 안인가
- 불필요한 호출·무한 반복·잘못된 재시도가 없는가
- 위험한 행동 전에 확인·승인을 받았는가
- 실패했을 때 안전하게 중단하거나 사람에게 넘겼는가
- 최종 작업이 실제로 완료되었는가

에이전트가 말로는 성공했다고 해도 데이터베이스 변경·티켓 생성·예약 완료 같은 실제 상태를 확인해야 합니다.

### 워크플로 평가

정해진 여러 단계를 순서대로 실행하는 워크플로는 단계별 성공률·전체 완료율·실패 단계·재시도 횟수·처리 시간·비용을 측정합니다. 한 단계의 답변 품질만 좋아져도 전체 작업 완료율이 낮으면 비즈니스 목표를 달성했다고 보기 어렵습니다.

## 비즈니스 지표

### 생산성

작업 한 건을 완료하는 시간, 상담원이 수정하는 시간, 처리량, 자동화된 단계의 비율을 측정합니다. “답변이 자연스럽다”보다 실제 업무 시간이 줄었는지가 중요할 수 있습니다.

### 사용자 참여

사용 빈도, 재사용률, 세션 유지, 추천 수락률 등 사용자가 실제로 기능을 활용하는 정도를 측정합니다. 참여 증가가 항상 좋은 결과는 아니므로 오류·불만·과도한 사용 비용과 함께 봅니다.

### 작업 완료율

사용자가 목표를 성공적으로 완료한 비율입니다. 에이전트가 답변을 잘 써도 티켓 생성·환불·예약 같은 실제 목표가 완료되지 않으면 작업 완료율은 낮을 수 있습니다.

### 사용자 만족도

설문·평점·재문의·사람에게 전환된 비율 등으로 사용자의 경험을 확인합니다. 평가 응답이 특정 사용자 그룹에 치우치지 않는지 살핍니다.

### 상호 작용당 비용

한 번의 질문·대화·완료 작업에 사용된 모델 호출, 검색, 도구, 저장·관찰 비용을 합산합니다. 품질을 조금 높이기 위해 비용이 크게 증가한다면 업무 가치와 비교합니다.

## 모델 지표와 비즈니스 지표의 정렬

```text
모델 지표: ROUGE·BLEU·BERTScore·사람 평가
       ↓ 품질·안전·근거 확인
애플리케이션 지표: 검색 성공·도구 정확성·지연·오류
       ↓ 실제 업무 확인
비즈니스 지표: 생산성·완료율·만족도·상호 작용당 비용
```

예를 들어 요약의 BLEU 점수가 올랐지만 상담원이 수정하는 시간이 늘었다면 성공으로 판단할 수 없습니다. 반대로 표현이 참조 문장과 달라도 상담원이 빠르게 검토하고 업무를 완료한다면 실제 가치가 있을 수 있습니다.

## 실무형 시나리오

회사가 RAG 기반 고객지원 에이전트를 출시한다고 가정합니다.

1. 벤치마크와 실제 고객 질문을 섞은 평가 데이터세트를 만듭니다.
2. 사람 평가로 답변의 정확성·근거성·안전성을 확인합니다.
3. RAG 검색 적중·관련성·출처 포함률과 생성 답변 품질을 분리해 봅니다.
4. 에이전트가 올바른 도구를 선택하고 실제 티켓을 성공적으로 생성했는지 확인합니다.
5. LLM-as-a-judge로 대량 비교를 보조하되, 사람 검토로 평가자 모델의 기준을 검증합니다.
6. 출시 후 상담원 처리 시간, 작업 완료율, 만족도, 재문의율, 상호 작용당 비용을 모니터링합니다.
7. 점수가 좋은데 실제 업무가 나빠지면 평가 데이터·프롬프트·검색·도구·비즈니스 지표의 연결을 다시 점검합니다.

## 시험에서 판단하는 단서

- “사람이 답변을 읽고 품질을 점수화” → 인간 평가
- “고정된 데이터와 과제로 모델을 비교” → 벤치마크 데이터세트
- “AWS 관리형 평가 작업” → Amazon Bedrock 모델 평가
- “참조 요약과 겹치는 단어·구문” → ROUGE
- “번역 결과와 참조 문장의 n-그램 비교” → BLEU
- “임베딩 기반 의미 유사성” → BERTScore
- “다른 LLM이 응답을 점수화·설명” → LLM-as-a-judge
- “RAG 품질” → 검색 관련성·완전성·근거성·출처·생성 품질을 분리
- “에이전트 성능” → 도구 선택·입력·안전 승인·작업 완료·실제 상태 확인
- “비즈니스 효과” → 생산성·참여·완료율·만족도·상호 작용당 비용

## 자주 하는 오해

### 오해 1: ROUGE·BLEU 점수가 높으면 답변이 사실이다

이 지표는 참조 텍스트와의 겹침을 평가하는 데 도움을 주지만 사실성·최신성·안전성·업무 유용성을 모두 측정하지 않습니다.

### 오해 2: 벤치마크 1위 모델이 모든 업무에서 최선이다

벤치마크는 특정 데이터와 과제의 결과입니다. 실제 사용자·언어·도메인·비용·지연·보안 조건으로 다시 평가해야 합니다.

### 오해 3: LLM-as-a-judge는 사람 평가를 완전히 대체한다

평가자 모델의 편향과 기준 오류가 있을 수 있습니다. 사람 평가·표본 검토·업무 지표와 함께 사용합니다.

### 오해 4: 에이전트가 성공 메시지를 반환하면 작업이 성공했다

최종 문장과 실제 외부 시스템 상태가 다를 수 있습니다. 티켓·주문·환불·예약의 실제 상태를 확인합니다.

### 오해 5: 모델 지표만 개선하면 비즈니스 성과도 개선된다

품질 점수와 실제 작업 완료율·처리 시간·만족도·비용의 관계를 측정해야 합니다.

## 핵심 정리

- 평가 목적·대표 데이터·기준·임계값을 먼저 정의합니다.
- 인간 평가·벤치마크·Amazon Bedrock 모델 평가·LLM-as-a-judge를 목적에 맞게 조합합니다.
- ROUGE·BLEU·BERTScore는 서로 다른 텍스트 유사성 관점을 제공하지만 만능 지표가 아닙니다.
- RAG는 검색과 생성을 분리해 평가하고, 에이전트는 도구 사용과 실제 작업 완료까지 확인합니다.
- 생산성·사용자 참여·작업 완료율·만족도·상호 작용당 비용을 모델 지표와 연결합니다.

**한 문장 암기 포인트:** `모델 점수 → 애플리케이션 행동 → 실제 비즈니스 결과`의 세 층을 모두 평가해야 합니다.

## 스스로 답하는 확인 질문

1. 인간 평가와 벤치마크 데이터세트의 장단점은 무엇인가요?
2. ROUGE·BLEU·BERTScore가 측정하는 관점의 차이를 말해 보세요.
3. LLM-as-a-judge 결과를 사람 평가와 함께 봐야 하는 이유는 무엇인가요?
4. RAG에서 검색 평가와 생성 평가를 분리해야 하는 이유는 무엇인가요?
5. 에이전트가 실제로 작업을 완료했는지 어떻게 확인할 수 있나요?
6. 모델 품질 점수와 함께 볼 비즈니스 지표를 세 가지 제안해 보세요.
