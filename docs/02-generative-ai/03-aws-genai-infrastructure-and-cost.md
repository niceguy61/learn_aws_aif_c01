# AWS GenAI 인프라·기술과 비용·성능 절충

## 이 문서에서 배울 것

이 문서에서는 Amazon Bedrock, Amazon SageMaker AI, Amazon SageMaker JumpStart, Amazon Q, Kiro, Strands Agents, Amazon Bedrock AgentCore의 역할을 구분합니다. 또한 토큰 기반 요금, 프로비저닝 처리량, 사용자 지정 모델 비용을 이해하고, 리전·보안·규정 준수·지연 시간·가용성·중복성·성능·비용을 함께 비교하는 방법을 배웁니다.

서비스의 세부 기능·모델 목록·요금·리전 지원은 변경될 수 있습니다. 아래 내용은 **2026-09-04에 확인한 공식 자료를 바탕으로 한 학습용 구분**이며, 실제 도입 전에는 각 서비스의 최신 공식 문서를 다시 확인해야 합니다.

## 선수 지식과 한 줄 요약

- 선수 지식: D2의 파운데이션 모델, 토큰, 에이전트, 모델 선택 기준을 알고 있으면 좋습니다.
- 한 줄 요약: **관리형 서비스는 인프라 부담을 줄이고, 모델 개발 플랫폼은 제어 범위를 넓히며, 비용·성능 선택은 요청량과 품질·보안 요구를 함께 보고 결정합니다.**

## 핵심 개념

### 관리형 서비스와 모델 개발 플랫폼

관리형 서비스는 사용자가 서버·모델 호스팅·확장 인프라를 직접 운영하는 부담을 줄여 줍니다. 대신 세부 제어 범위, 지원되는 모델과 기능, 서비스별 요금 구조를 확인해야 합니다.

모델 개발 플랫폼은 데이터 준비, 모델 선택·훈련·사용자 지정·배포·모니터링처럼 모델 개발 수명 주기에 더 넓게 관여할 수 있게 합니다. 자유도가 커지는 만큼 데이터, 컴퓨팅, 배포, 운영을 계획할 책임도 커질 수 있습니다.

### 토큰 기반 가격

많은 생성형 AI 모델 호출 비용은 입력 토큰과 출력 토큰의 양을 기준으로 계산됩니다. 같은 요청 횟수라도 다음 조건에 따라 비용이 달라질 수 있습니다.

- 입력 프롬프트와 컨텍스트가 얼마나 긴가
- 모델이 생성하는 출력이 얼마나 긴가
- 어떤 모델 제공자·모델·모달리티를 사용하는가
- 온디맨드, 배치, 예약·프로비저닝 같은 어떤 가격 계층을 사용하는가

따라서 “월 1만 건 호출”만으로 비용을 추정할 수 없습니다. 다음처럼 분해해야 합니다.

```text
월 비용 추정
= 요청 수 × (평균 입력 토큰 비용 + 평균 출력 토큰 비용)
  + 검색·임베딩·저장·도구 호출·모니터링 등 관련 비용
```

위 식은 개념을 위한 구조입니다. 실제 단가는 모델과 리전에 따라 달라지므로 가격표에서 확인합니다.

### Provisioned Throughput

Provisioned Throughput은 모델이 처리할 입력·출력 처리량을 일정 수준으로 확보하기 위해 구매하는 용량 방식입니다. 트래픽이 예측 가능하고 일정한 처리량이나 더 예측 가능한 성능이 필요한 경우 검토할 수 있습니다.

반대로 요청량이 작거나 변동이 크고 먼저 실험하려는 단계라면 온디맨드 호출이 더 단순할 수 있습니다. Provisioned Throughput은 “항상 가장 저렴한 방식”이 아니라, 예측 가능한 처리량·지연 시간과 비용 구조가 필요한지 판단하는 선택지입니다.

Amazon Bedrock에서 사용자 지정 모델을 사용하려는 경우에는 해당 모델을 사용할 수 있도록 필요한 프로비저닝 조건을 공식 문서에서 확인해야 합니다.

### 사용자 지정 모델 비용

사용자 지정 모델은 일반적인 모델 호출 비용만으로 끝나지 않을 수 있습니다. 데이터 준비·정제, 사용자 지정 또는 미세 조정에 필요한 작업, 모델 배포·추론 용량, 평가·모니터링 비용을 함께 고려합니다.

사용자 지정이 항상 프롬프트보다 좋은 것도 아닙니다. 업무 지식이 최신 문서에 있고 답변 때 검색해서 제공할 수 있다면 RAG가 더 적합할 수 있습니다. 반대로 출력 형식·행동 방식·도메인 표현을 반복해서 학습시켜야 한다면 미세 조정을 비교할 수 있습니다. 이 판단은 D3에서 더 깊게 다룹니다.

## AWS 관점과 관련 서비스

### Amazon Bedrock

[Amazon Bedrock](https://aws.amazon.com/bedrock/)은 여러 공급자의 파운데이션 모델을 API로 사용할 수 있도록 하는 관리형 생성형 AI 서비스입니다. 애플리케이션 팀은 모델을 직접 호스팅하는 대신 모델 선택·호출·평가·지식 연결·에이전트와 같은 애플리케이션 기능에 집중할 수 있습니다.

**언제 검토하나요?**

- 여러 FM을 비교하거나 교체할 가능성이 있는 생성형 AI 애플리케이션
- 모델 호스팅 인프라를 직접 운영하고 싶지 않은 경우
- 모델 호출, 지식 연결, 안전성 제어를 AWS 관리형 기능과 함께 구성하려는 경우

Bedrock은 “모델을 직접 훈련하는 서비스”라는 뜻이 아닙니다. 미리 준비된 FM을 호출하고, 필요에 따라 사용자 지정·검색·에이전트 기능을 조합하는 관리형 애플리케이션 경로로 이해합니다.

### Amazon SageMaker AI

[Amazon SageMaker AI](https://aws.amazon.com/sagemaker-ai/)는 데이터를 준비하고, 모델을 만들거나 선택하고, 훈련·사용자 지정·배포·관리하는 ML 개발 플랫폼입니다. 모델 개발 수명 주기에 직접 관여해야 하거나 훈련·추론 인프라와 운영을 더 세밀하게 제어해야 하는 경우 검토합니다.

**언제 검토하나요?**

- 자체 데이터로 모델을 훈련·미세 조정·평가해야 하는 경우
- 생성형 AI뿐 아니라 전통적인 ML 모델도 같은 개발·운영 환경에서 다뤄야 하는 경우
- 훈련 작업, 엔드포인트, 컴퓨팅 유형과 배포 방식을 더 세밀하게 선택해야 하는 경우

### Amazon SageMaker JumpStart

[Amazon SageMaker JumpStart](https://aws.amazon.com/sagemaker-ai/jumpstart/)는 사전 훈련된 모델과 ML 자산을 찾아 실험·사용자 지정·배포하는 데 도움을 주는 SageMaker AI의 진입점으로 이해할 수 있습니다.

**구분 포인트:** JumpStart는 독립된 “모든 모델을 대신 운영하는 API 서비스”라기보다, SageMaker AI 환경에서 사전 훈련 모델을 선택하고 개발을 빠르게 시작하도록 돕는 기능입니다.

### Amazon Q

[Amazon Q](https://aws.amazon.com/q/)는 조직의 업무와 개발을 돕는 생성형 AI 어시스턴트 제품군입니다. 사용자는 자연어로 업무 데이터·정책·코드·개발 작업에 관한 도움을 받을 수 있습니다. Amazon Q는 Amazon Bedrock을 기반으로 하며, 사용자의 권한과 연결된 데이터 접근 제어가 중요합니다.

**구분 포인트:**

- Amazon Q: 바로 사용할 수 있는 조직·개발자용 어시스턴트 경험
- Amazon Bedrock: 애플리케이션 개발자가 FM을 선택·호출하고 GenAI 애플리케이션을 구성하는 플랫폼
- SageMaker AI: 모델 개발·훈련·사용자 지정·배포를 더 폭넓게 다루는 플랫폼

### Kiro

[Kiro](https://aws.amazon.com/documentation-overview/kiro/)는 프롬프트에서 상세한 사양과 구현 산출물로 이어지는 작업을 지원하는 agentic 개발 환경입니다. 이 문서에서 Kiro는 모델 호스팅 서비스나 추론 엔드포인트가 아니라 **AI를 활용한 소프트웨어 개발 도구**로 구분합니다.

시험 문제에서 Kiro가 등장한다면 Amazon Bedrock이나 SageMaker AI와 같은 모델 실행·개발 인프라와 혼동하지 말고, 개발자 생산성과 사양 기반 작업 흐름에 연결합니다.

### Strands Agents

[Strands Agents](https://aws.amazon.com/de/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/)는 모델이 도구를 사용하고 여러 단계를 수행하는 에이전트를 만들기 위한 오픈 소스 SDK입니다. 에이전트의 행동 흐름과 도구 연결을 코드·구성으로 설계하는 개발자 관점의 도구이며, 그 자체가 FM을 제공하는 서비스는 아닙니다.

### Amazon Bedrock AgentCore

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)는 에이전트를 구축·연결·보호·운영하기 위한 관리형 플랫폼입니다. 에이전트 런타임, 도구 연결, 메모리·보안·관찰 같은 운영 요구를 직접 조합해야 하는 부담을 줄이는 방향으로 이해할 수 있습니다.

**구분 포인트:** Strands Agents가 에이전트 개발 SDK라면, AgentCore는 에이전트를 운영 환경에 연결하고 확장·보호하기 위한 관리형 실행·운영 기반입니다. 실제 사용 가능한 구성 요소와 리전·요금은 변경될 수 있으므로 최신 공식 문서에서 확인합니다.

## 리전·보안·규정 준수

### 리전 선택

리전은 단순히 지연 시간이 가까운 위치만을 뜻하지 않습니다. 원하는 모델과 기능의 제공 여부, 데이터 처리 위치, 조직의 데이터 레지던시 요구, 서비스별 가격과 할당량, 장애 대응 전략을 함께 확인해야 합니다.

시험에서는 “특정 리전에서 필요한 모델을 사용할 수 없음”, “데이터가 특정 지역을 떠나면 안 됨”, “사용자와 가까운 곳에서 지연 시간을 줄여야 함” 같은 단서를 구분할 수 있어야 합니다. 어떤 리전에서 어떤 기능이 제공되는지는 현재 공식 리전별 서비스 문서를 확인합니다.

### 보안과 규정 준수

생성형 AI 애플리케이션은 모델보다 데이터 흐름이 더 큰 위험을 만들 수 있습니다. 다음 질문을 먼저 확인합니다.

- 누가 모델과 애플리케이션을 호출할 수 있는가
- 입력에 개인정보·기밀 정보가 포함되는가
- 모델·검색 저장소·도구가 어떤 데이터에 접근하는가
- 전송 중·저장 중 데이터를 어떻게 보호하는가
- 요청·응답·도구 호출을 감사하고 추적할 수 있는가
- 조직의 보존·삭제·데이터 레지던시 정책을 만족하는가

IAM 권한, 암호화, 네트워크 경로, 로그 접근 권한, 출력 필터, 사람 검토를 함께 설계해야 합니다. “관리형 서비스이므로 보안 책임이 모두 AWS에 있다”는 해석은 올바르지 않습니다. AWS와 고객의 책임 범위는 서비스와 구성에 따라 달라집니다.

## 비용·성능·가용성 절충

### 주요 절충표

| 선택 | 얻는 것 | 부담·위험 |
|---|---|---|
| 더 큰 모델 | 복잡한 작업에서 품질·추론 능력 향상 가능 | 토큰 비용과 지연 시간 증가 가능 |
| 더 작은 모델 | 낮은 비용과 빠른 응답 가능 | 복잡한 작업 품질이 부족할 수 있음 |
| 긴 컨텍스트 | 더 많은 정보 제공 가능 | 입력 토큰 비용·지연·관련 없는 정보 증가 |
| 온디맨드 호출 | 초기 실험과 변동 트래픽에 단순함 | 처리량·지연 시간 예측이 어려울 수 있음 |
| Provisioned Throughput | 예측 가능한 처리량과 성능을 계획하기 쉬움 | 고정 비용·용량 계획·약정 검토 필요 |
| 단일 리전 | 구조와 비용이 단순함 | 리전 장애 시 복구 선택지가 제한될 수 있음 |
| 다중 리전·중복성 | 장애 대응과 가용성 향상 가능 | 비용·데이터 동기화·운영 복잡성 증가 |
| 사용자 지정 모델 | 특정 업무 표현·형식에 맞출 가능성 | 데이터·훈련·배포·평가 비용과 관리 부담 |
| 사전 훈련 모델 + 프롬프트/RAG | 빠른 시작과 최신 자료 연결 가능 | 컨텍스트 품질·검색 품질·프롬프트 설계 필요 |

### 지연 시간과 성능

응답 시간은 모델 크기, 입력·출력 토큰 수, 요청량, 네트워크·검색·도구 호출, 서비스 용량의 영향을 받을 수 있습니다. “정확도가 가장 높은 모델”이 사용자 대화에 항상 최선은 아닙니다. 사용자가 허용할 수 있는 지연 시간과 필요한 품질을 함께 측정합니다.

성능을 비교할 때는 평균값만 보지 않고, 실제 업무 질문을 대표하는 평가 집합으로 품질과 지연 시간·비용을 함께 비교합니다.

### 가용성과 중복성

중요한 업무에서는 한 번의 모델 호출이 실패하거나 지연될 때의 동작을 정의합니다. 재시도, 대체 모델, 대체 응답, 큐잉, 사람에게 전달하는 경로를 설계할 수 있습니다.

다중 리전 중복성은 가용성을 높일 수 있지만, 데이터 레지던시·동기화·비용·운영 복잡성을 증가시킬 수 있습니다. 가용성 목표가 높다는 이유만으로 무조건 다중 리전을 선택하지 않고, 업무 손실과 복구 목표를 기준으로 결정합니다.

## 실무형 시나리오

온라인 쇼핑몰이 상품 설명 요약과 고객 상담 초안을 제공하려고 합니다.

1. 초기에는 트래픽이 불확실하므로 Amazon Bedrock의 온디맨드 모델 호출로 여러 FM을 비교합니다.
2. 상품 정보는 검색으로 제공하고, 모델이 최신 가격을 임의로 만들지 않도록 답변 근거와 검증 규칙을 둡니다.
3. 고객 상담이 늘어 지연 시간과 처리량이 일정해야 하면 Provisioned Throughput을 비용과 함께 비교합니다.
4. 상담 초안은 자동 생성하되 환불·보상 결정은 상담원이 승인합니다.
5. 월 비용은 입력·출력 토큰뿐 아니라 임베딩·검색·저장·로그·도구 호출 비용까지 포함해 계산합니다.
6. 장애 시 대체 응답과 상담원 전달 경로를 마련하고, 개인정보가 다른 리전으로 이동하지 않는지 확인합니다.

이 시나리오에서 가장 비싼 모델을 고르는 것이 답이 아닙니다. **요구 품질을 만족하는 가장 단순한 구성에서 시작하고, 측정 결과에 따라 모델·처리량·중복성을 확장**하는 것이 핵심입니다.

## 시험에서 판단하는 단서

- “여러 공급자의 FM을 API로 선택·호출하고 인프라 관리를 줄임” → Amazon Bedrock
- “모델 훈련·사용자 지정·배포·ML 수명 주기 관리” → Amazon SageMaker AI
- “사전 훈련 모델을 찾아 빠르게 실험·배포” → SageMaker JumpStart
- “조직 데이터와 개발 업무를 돕는 바로 사용 가능한 어시스턴트” → Amazon Q
- “에이전트를 코드로 만들고 도구를 연결” → Strands Agents
- “운영 환경에서 에이전트를 연결·보호·확장” → Amazon Bedrock AgentCore
- “입력·출력 크기에 따라 호출 비용이 달라짐” → 토큰 기반 가격
- “예측 가능한 처리량과 일정한 성능이 중요함” → Provisioned Throughput 검토
- “모델을 고르는 문제” → 품질만이 아니라 비용·지연 시간·보안·리전·가용성 비교

## 자주 하는 오해

### 오해 1: Amazon Bedrock과 SageMaker AI는 같은 서비스다

둘 다 AI와 관련 있지만 중심이 다릅니다. Bedrock은 FM을 활용한 애플리케이션 구성에, SageMaker AI는 모델 개발·훈련·사용자 지정·배포의 폭넓은 수명 주기에 초점을 둡니다. 실제 서비스 기능은 겹칠 수 있으므로 문제의 핵심 요구를 읽습니다.

### 오해 2: Provisioned Throughput은 호출당 비용을 없앤다

프로비저닝은 처리량을 확보하는 가격·용량 방식입니다. 모델·요금 조건에 따라 비용이 계산되며, 고정 용량과 사용 패턴이 맞는지 비교해야 합니다.

### 오해 3: Amazon Q는 고객 데이터에 무조건 접근한다

조직 데이터 연결과 권한 설정이 전제입니다. 사용자가 접근할 권한이 없는 데이터는 애플리케이션에서도 제공하지 않도록 권한 경계를 설계해야 합니다.

### 오해 4: 관리형 서비스면 고객이 신경 쓸 인프라가 없다

서버 패치 같은 부담은 줄어들 수 있지만 IAM, 데이터 접근, 네트워크, 리전, 비용, 로그, 출력 검증은 여전히 설계 대상입니다.

### 오해 5: 다중 리전이면 모든 문제가 해결된다

다중 리전은 가용성 선택지 중 하나일 뿐입니다. 데이터 이동 제한, 일관성, 비용, 운영 복잡성까지 충족할 때 선택합니다.

## 핵심 정리

- Amazon Bedrock은 여러 FM을 활용하는 관리형 GenAI 애플리케이션 플랫폼입니다.
- Amazon SageMaker AI는 모델 개발·훈련·사용자 지정·배포를 폭넓게 지원하는 ML 플랫폼입니다.
- SageMaker JumpStart는 사전 훈련 모델을 찾아 SageMaker AI에서 빠르게 시작하도록 돕습니다.
- Amazon Q는 조직·개발자 업무를 돕는 생성형 AI 어시스턴트입니다.
- Strands Agents는 에이전트 개발 SDK이고, AgentCore는 에이전트 운영·연결·보호 기반입니다.
- Kiro는 모델 실행 서비스가 아니라 AI 지원 소프트웨어 개발 환경으로 구분합니다.
- 토큰 기반 가격은 입력·출력 양과 모델·가격 계층에 따라 달라집니다.
- 온디맨드와 Provisioned Throughput은 트래픽·처리량·지연 시간·비용을 비교해 선택합니다.
- 리전·보안·규정 준수·가용성·중복성은 모델 선택만큼 중요한 설계 조건입니다.

**한 문장 암기 포인트:** `Bedrock은 FM 활용`, `SageMaker AI는 모델 개발`, `Q는 업무 어시스턴트`, `AgentCore는 에이전트 운영 기반`입니다.

## 스스로 답하는 확인 질문

1. 모델을 직접 훈련하지 않고 여러 FM을 비교해 생성형 AI 애플리케이션을 만들려면 어떤 서비스를 먼저 검토하나요?
2. 자체 데이터로 모델을 훈련·사용자 지정하고 배포까지 관리해야 한다면 어떤 서비스가 중심인가요?
3. 입력 토큰과 출력 토큰이 비용에 미치는 영향을 설명해 보세요.
4. 요청량이 일정하고 지연 시간과 처리량을 예측해야 할 때 온디맨드와 무엇을 비교하나요?
5. Strands Agents와 Amazon Bedrock AgentCore의 역할 차이를 말해 보세요.
6. 모델 성능이 좋아도 도입하지 않을 수 있는 이유를 비용·보안·리전 관점에서 각각 하나씩 말해 보세요.
