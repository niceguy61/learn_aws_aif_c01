## Contribution

리드 초안은 Greenfield 정적 한국어 Markdown 저장소의 성격을 잘 반영하고 있다. trunk-based 작업, 작은 문서 단위, 출처·링크·초보자 관점의 정적 검증을 제안한 방향에 동의한다. 다만 실제 집필이 시작되면 파일 식별, 문서 메타데이터, 공식 범위 추적, 검증 결과 보존을 사람이 해석하지 않아도 일관되게 확인할 수 있도록 몇 가지 운영 규칙을 더 구체화할 필요가 있다.

특히 애플리케이션 코드가 없다는 이유로 문서 저장소의 품질 계약을 느슨하게 두면, 같은 개념의 문서가 서로 다른 이름과 형식을 사용하거나 출처가 문서마다 흩어질 수 있다. 따라서 문서 파일 자체와 출처 인벤토리, 공식 시험 범위 추적표 사이의 연결을 안정적인 식별자로 유지하는 것이 실질적인 구현 품질에 해당한다.

## Positions

### 명명

- 제안에 동의한다. 디렉터리와 파일명은 영문 소문자·숫자·하이픈만 사용하고, 도메인 번호와 의미를 함께 드러내는 현재의 구조를 유지하는 것이 좋다.
- 문서 파일명은 같은 디렉터리 안에서 고유해야 하며, 제목의 임의 번역이나 날짜를 파일명에 넣지 않는 편이 좋다. 날짜와 검증 상태는 문서 메타데이터와 출처 기록으로 관리해야 한다.
- 용어 문서, 도메인 안내서, 개념 문서의 역할을 파일명만으로 구분할 수 있도록 `README.md`는 디렉터리 안내용으로만 사용하고, 학습 개념은 구체적인 하이픈 이름을 사용해야 한다.
- AWS 서비스명이나 API명이 파일명에 들어갈 때에도 파일 시스템 규칙을 우선하되, 본문 제목과 YAML 메타데이터에서는 공식 표기를 보존해야 한다.

### 파일 조직

- `docs/00-start-here`부터 `docs/06-exam-strategy`까지의 상위 구분과 `sources`, `plans`의 분리는 정적 학습 저장소에 적합하다.
- 각 도메인 디렉터리의 `README.md`에는 학습 순서뿐 아니라 해당 도메인의 공식 시험 작업·기술 항목과 연결된 문서 목록을 두어야 한다. 문서가 아직 없으면 누락이 아니라 `확장` 또는 `해당 없음`으로 명시해야 한다.
- 한 문서에 여러 독립 개념을 몰아넣지 말자는 방향에 동의한다. 다만 개념 문서를 지나치게 잘게 나누면 링크 관리가 어려워지므로, 학습 목표·확인 질문·출처가 하나의 단위로 유지되는 범위를 파일 경계로 삼는 것이 좋다.
- 출처 인벤토리와 학습 문서는 별도 파일로 유지하되, 문서 본문에서 출처의 URL을 직접 연결하고 인벤토리에는 연결 문서 경로를 기록해야 한다. 한쪽만 갱신되는 상태를 막기 위해 정적 검사 항목을 추가할 필요가 있다.
- `plans`는 사용자 승인 전 초안과 승인 후 결정을 구분해야 한다. 승인된 목차와 질문 답변은 문서 집필 산출물과 섞지 않고 계획 파일에 남겨야 한다.

### Markdown과 front matter 일관성

- 모든 도메인 학습 문서에 동일한 YAML front matter 필드 집합을 적용하는 것에 동의한다. 최소한 `title`, `domain`, `level`, `status`, `source_urls`, `source_checked`를 요구해야 한다.
- `status`는 사용자 승인 상태와 출처 검증 상태를 혼동하지 않도록 정의를 고정해야 한다. 사용자 승인 전의 문서는 `draft`를 유지하고, 공식 출처와 내용 검토를 끝낸 경우에만 `verified`로 올리는 규칙이 필요하다.
- `source_urls`가 비어 있지 않은지, URL이 본문 또는 `출처` 섹션과 실제로 연결되는지, `source_checked`가 유효한 날짜인지 자동 검사해야 한다.
- 문서 내부 순서와 제목 수준을 표준화하면 초보자용 문서 간 이동이 쉬워진다. 특히 `출처`, `핵심 정리`, `스스로 답하는 확인 질문`, `연결된 다음 문서` 같은 필수 섹션의 누락을 검사해야 한다.
- 표와 코드 블록의 사용 규칙도 정적 검사 대상에 포함하는 것이 좋다. 넓은 표, 설명 없는 Mermaid 의존, 언어가 표시되지 않은 코드 블록은 모바일 가독성과 접근성을 해칠 수 있다.
- YAML 값에 콜론, 해시, 따옴표가 포함될 수 있으므로 모든 문서가 동일한 인용 규칙을 사용해야 한다. 파서가 실패하는 front matter는 내용 검토 이전에 차단해야 한다.

### 안정적인 ID

- 현재 초안에는 공식 시험 범위, 작업·기술 항목, 문서, 출처를 연결할 안정적인 ID 규칙이 명시되어 있지 않다. D1부터 D5까지의 도메인에는 `D1`부터 `D5`를 사용하고, 시험 작업과 기술 항목에도 변경되지 않는 ID를 부여해야 한다.
- 문서에는 예를 들어 `DOC-D1-001`과 같은 문서 ID를 front matter에 두고, 출처에는 `SRC-001`과 같은 출처 ID를 부여하면 제목이나 파일명이 바뀌어도 추적을 유지할 수 있다.
- 시험 범위 항목과 문서의 연결은 문서 제목의 문자열 일치에 의존하지 말고 문서 추적표의 ID와 경로로 관리해야 한다. 이동·분할·통합이 발생하면 기존 ID를 폐기할지 승계할지 기록해야 한다.
- ID는 재사용하지 않아야 한다. 문서를 삭제하거나 `해당 없음`으로 바꾸더라도 그 ID의 상태와 사유를 추적표에 남겨야 과거 검토 결과가 다른 문서로 잘못 연결되지 않는다.
- 용어 사전 항목에도 가능하면 안정적인 용어 ID를 부여해야 한다. 동일한 AWS 서비스명과 핵심 개념이 여러 도메인에서 등장할 때 정의가 분기되는 문제를 줄일 수 있다.

### 출처와 문서 추적성

- 공식 AIF-C01 시험 안내서를 범위의 기준으로 삼고, AWS 공식 문서·Skill Builder·공식 블로그를 학습 보조 출처로 구분하자는 방향을 지지한다.
- `sources/aws-sidebar-index.md`에는 사이드바 링크를 생략 없이 기록하고, `source-registry.yaml`에는 URL, 제목, 출처 유형, 주 도메인·보조 도메인, 확인일, 접근 상태, 연결 문서 ID를 저장해야 한다.
- 문서가 주장하는 변동 가능 사실은 문서의 `출처` 섹션과 레지스트리 양쪽에서 확인할 수 있어야 한다. 어느 한쪽에만 있는 URL은 추적성 경고로 처리하는 것이 좋다.
- 페이지 접근이 차단되거나 동적 내용으로 확인되지 않은 경우에는 요약을 작성하지 말고 `blocked` 상태와 확인 실패 사유를 기록해야 한다. 대체 출처를 사용하면 대체 이유와 원래 출처의 관계도 남겨야 한다.
- 출처 확인일은 단순 작성일과 구분해야 한다. 서비스 기능, 모델명, 요금, 리전, 할당량은 재검증 주기를 정하고, 오래된 출처를 자동으로 `확인 필요` 후보로 표시하면 실무적인 최신성 관리가 가능하다.
- 공식 시험 범위와 실무 확장 내용을 같은 문서에서 다룰 때는 각각을 명확히 표시해야 한다. 확장 내용이 시험 출제 범위처럼 읽히지 않도록 별도 표식 또는 별도 절을 사용해야 한다.

### 정적 문서 저장소의 실질적 보완점

- `test-after` 제안에 동의하되, 검사 명령과 통과 기준을 별도로 문서화해야 한다. 예를 들면 Markdown 문법, front matter 파싱, 외부 링크 형식, 내부 링크 대상, 출처 레지스트리 참조, 시험 범위 누락 검사를 구분해 실행해야 한다.
- 문서 하나를 작성한 뒤 검사하는 것만으로는 문서 간 불일치를 찾기 어렵다. 도메인 단위와 전체 저장소 단위에서 중복 ID, 고아 출처, 끊어진 내부 링크, 추적표에 없는 문서를 검사해야 한다.
- 자동 링크 검사는 외부 사이트의 일시적 오류와 실제 링크 변경을 구분해야 한다. 네트워크 확인이 실패한 경우 문서를 곧바로 `verified`에서 내리지 말고, 확인 시각과 재시도 필요 상태를 기록해야 한다.
- 초보자 관점 검토는 정적 도구만으로 완전히 대체할 수 없다. 문서마다 선수 지식, 쉬운 예시, AWS 서비스 선택 단서, 오해, 확인 질문이 있는지 검사하고, 별도의 사람 검토 결과를 기록해야 한다.
- 문서 변경 시 출처와 추적표를 함께 갱신하도록 검토 체크리스트나 검사 실패를 통합 조건에 포함해야 한다. 그렇지 않으면 작은 Markdown 변경이 공식 근거와 어긋난 채 남을 수 있다.
- 유료 실습과 코드 구현을 필수로 요구하지 않는 제약은 유지하되, 명령·JSON·의사코드가 포함된 문서의 예시는 실행 필수 항목이 아닌 이해 보조 예시임을 표시해야 한다.
- `verified` 승격 조건에는 사용자 승인, 출처 확인, 초보자 검토, 범위 추적 검사를 각각 포함해야 한다. 하나의 종합 상태로 압축하면 어떤 검토가 끝났는지 알기 어렵다.

### 종합 입장

현재 제안은 방향상 수용 가능하지만, 사용자 확인 전에는 계속 `제안` 또는 `확인 필요` 상태로 유지해야 한다. 승인 단계에서는 특히 안정적인 ID 체계, front matter 필수 필드, 검사 명령과 통과 기준, 외부 링크 실패 처리, `verified` 승격 조건을 명시적으로 결정해야 한다. 이 항목들이 정해져야 문서가 늘어난 뒤에도 명명·조직·출처 추적성이 사람의 기억에 의존하지 않는다.
