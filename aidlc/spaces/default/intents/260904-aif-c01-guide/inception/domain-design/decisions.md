## ADR-001: 네 개의 논리적 책임 컴포넌트로 분해

- **Context** — 프로젝트는 실행형 애플리케이션이 아니지만, 공식 기준선·학습 문서·평가 자료·품질 증거의 변경 주기와 검토 책임이 다르다. 모든 내용을 하나의 `DomainContent`로 묶으면 출처·콘텐츠·문항·검증 경계가 섞인다.
- **Decision** — `ReferenceCatalog`, `LearningContent`, `AssessmentContent`, `QualityEvidence` 네 개의 논리적 컴포넌트로 분해한다. 이들은 정적 산출물과 검토 책임을 설명하는 building block이며 배포 단위가 아니다.
- **Consequences** — 기준선·문서·평가·품질을 독립적으로 검토하고 변경할 수 있다. 컴포넌트 간 기준선·문서 참조가 필요하며, 중앙 추적표와 상대 링크를 함께 유지해야 한다. 보안·개인정보 측면에서는 학습자 데이터 저장 책임이 어느 컴포넌트에도 생기지 않는다.
- **Alternatives Rejected** — `DomainContent` 하나로 통합하는 방식은 구조가 단순하지만 책임과 변경 영향을 구분하기 어렵다. `VisualContent`와 `LearningSupport`까지 모두 별도 컴포넌트로 추가하는 방식은 선택적인 표현 형식과 평가 파일 형식에 과도한 경계를 만든다.

## ADR-002: 공식 기준선·출처의 단일 소유

- **Context** — 공식 시험 안내서의 revision, `AIF-C01-D<n>-T<n>` 행, 사이드바 링크, URL·제목·확인일·접근 상태가 여러 자료에 반복된다. 복제 소유는 서로 다른 확인일과 상태를 만들 위험이 있다.
- **Decision** — `ReferenceCatalog`가 `BaselineItem`, `SourceRecord`, `SidebarLink`를 소유한다. `LearningContent`와 `AssessmentContent`는 해당 ID와 링크를 참조하고, 문서·문항에는 독자가 확인할 수 있는 필요한 메타데이터를 표시한다.
- **Consequences** — 공식 범위와 출처 변경을 한 책임에서 추적할 수 있고 고아 기준선 검사가 가능하다. 파생 자료가 기준선 ID를 잃지 않도록 양방향 추적 검사가 필요하다. 출처가 `blocked`이면 파생 자료를 `verified`로 승격할 수 없다.
- **Alternatives Rejected** — 도메인별 문서가 출처를 복제하는 방식은 불일치 위험이 높다. 문서·문항에만 출처를 흩어 기록하는 방식은 전체 사이드바 완전성과 revision 비교를 재구성하기 어렵다.

## ADR-003: 상대 Markdown 링크와 중앙 추적표의 병행

- **Context** — 학습자는 GitHub-Flavored Markdown 또는 일반 Markdown 뷰어에서 시작 안내·도메인·이전/다음 문서·복습 자료를 이동해야 한다. 검토자는 공식 기준선에서 모든 파생 자료로, 파생 자료에서 기준선으로 이동하는 양방향 추적을 재구성해야 한다.
- **Decision** — 학습자 탐색의 기본은 안정 ID를 포함한 상대 Markdown 링크로 한다. 중앙 JSON/YAML 추적표는 원본 탐색 UI가 아니라 누락·고아·양방향 매핑 검사용으로 유지한다.
- **Consequences** — 외부 렌더러나 애플리케이션 없이 읽을 수 있고 링크 검사가 가능하다. 파일 이동 시 링크와 추적표를 함께 갱신해야 한다. 중앙 추적표만으로 모든 탐색을 대체하지 않는다.
- **Alternatives Rejected** — 중앙 JSON만 사용하는 방식은 정적 문서의 자연스러운 이동을 약화한다. 상대 링크만 사용하는 방식은 공식 기준선·문항·카드·퀴즈·Anki 전체의 기계적 완전성 검사를 어렵게 한다.

## ADR-004: 평가·복습 자료를 `AssessmentContent`에 통합

- **Context** — 문제은행·정적 점수 워크시트·카드·용어 퀴즈·Anki는 파일 형식은 다르지만 기준선 ID, 원본 문서, 범위 분류, 출처 메타데이터를 공유한다. 별도의 `LearningSupport`를 추가하면 책임 경계가 파일 형식에 따라 과도하게 분리된다.
- **Decision** — `AssessmentContent`가 `QuestionBankItem`, `ScoreSheet`, `Card`, `TermQuizItem`, `AnkiNote`를 모두 소유한다. 형식별 ID와 검증 규칙은 각각 유지하되, 논리적 소유자는 하나다.
- **Consequences** — 문제·복습 자료의 커버리지와 범위 표지를 한 책임에서 점검할 수 있다. 문항의 정답·오답·난이도·중복 검토와 CSV 파싱 검사는 서로 다른 검증 규칙으로 분리해 기록해야 한다. 점수 워크시트는 정적 로컬 수기 기록으로만 유지한다.
- **Alternatives Rejected** — 카드·퀴즈·Anki를 `LearningSupport`로 별도 분리하면 공통 추적·출처·범위 규칙을 중복 관리한다. 문제은행만 컴포넌트로 두면 핵심 복습 자료의 소유와 검증이 모호해진다.

## ADR-005: 시각 자료는 학습 문서에 귀속하고 AWS 공식 이미지 메타데이터만 출처 카탈로그가 소유

- **Context** — Mermaid와 이미지는 선택 사항이다. 핵심 의미는 외부 렌더러·이미지·색상 없이 읽혀야 하고, AWS 공식 이미지는 접근·권리·사용 조건을 확인해야 한다.
- **Decision** — 가이드 작성 도표와 텍스트 대체는 `LearningContent`가 학습 문서 가까이에 함께 관리한다. AWS 공식 이미지의 직접 URL·원본 페이지·제목·접근일·저작자 표시·사용 조건 메타데이터는 `ReferenceCatalog`가 관리한다. 조건이 불명확하면 이미지를 다운로드하거나 재배포하지 않는다.
- **Consequences** — 텍스트 우선 접근성과 권리 추적을 동시에 유지한다. `VisualContent`를 별도 컴포넌트로 만들지 않아 문서 의미와 대체 설명이 분리되지 않는다. 공식 이미지 사용 여부는 출처 검토를 통과해야 한다.
- **Alternatives Rejected** — 모든 시각 자료를 `VisualContent`로 분리하면 문서와 대체 설명이 멀어지고 선택적 기능에 과도한 경계가 생긴다. 이미지를 자유롭게 넣는 방식은 접근성·권리·AWS 보증 오해 위험을 통제하지 못한다.

## ADR-006: AWS 서비스는 외부 의존성·학습 참조 대상으로 처리

- **Context** — AIF-C01 가이드는 AWS 서비스를 설명하지만 AWS 서비스를 배포하거나 호출하는 애플리케이션을 만들지 않는다. 이 단계의 컴포넌트는 우리가 작성하는 논리적 책임 단위다.
- **Decision** — AWS Certification 공식 안내서와 AWS 공식 문서는 `ReferenceCatalog`의 외부 출처 의존성으로 기록한다. AWS 서비스명은 `LearningContent`의 설명·비교·시나리오와 `AssessmentContent`의 기준선 연결 대상이며, 서비스별 컴포넌트로 모델링하지 않는다.
- **Consequences** — 설계가 학습 콘텐츠 프로젝트의 실제 산출물과 일치하고 AWS 계정·리소스·비용·운영 책임이 추가되지 않는다. 변동 가능한 서비스 세부사항은 출처 확인일과 접근 상태를 관리해야 한다. 서비스 기능을 출제 범위로 단정하지 않도록 공식 기준선과 실무 확장 표지를 함께 검사한다.
- **Alternatives Rejected** — 서비스별 컴포넌트를 만드는 방식은 외부 학습 대상을 작성 코드로 오인한다. AWS 서비스를 단순 문자열로만 기록하면 공식 출처·revision·접근 상태와의 추적이 약해진다.

## ADR-007: 품질 증거의 중앙 소유와 콘텐츠와의 분리

- **Context** — 초보자 관점, 개념 단위, 링크·제목, 출처 상태, 범위 표지, 문항 품질, CSV 형식, 민감정보 검사는 여러 산출물에 걸쳐 반복된다. 검사를 콘텐츠 파일에만 흩어 쓰면 재검사와 최종 통합 판정이 어렵다.
- **Decision** — `QualityEvidence`가 `QualityCheckRecord`를 소유하고 대상 경로·검사일·검사자 또는 도구·판정·근거·조치·재검사 결과를 기록한다. 콘텐츠 컴포넌트는 품질을 통과한 것으로 표시할 수 있지만 품질 증거의 소유권은 갖지 않는다.
- **Consequences** — 도메인별 점검과 최종 통합 점검을 재구성할 수 있다. 품질 컴포넌트가 콘텐츠를 수정하지 않으므로 실패 시 원래 소유 컴포넌트가 수정하고 재검사를 요청해야 한다. 민감정보 검사는 예시·로그·CSV·출처 메타데이터까지 범위를 유지한다.
- **Alternatives Rejected** — 최종 단계에서만 검사하는 방식은 조기 누락 발견을 어렵게 한다. 각 파일에만 결과를 두는 방식은 중앙 품질 보고서와 재검사 이력을 만들기 어렵다.
