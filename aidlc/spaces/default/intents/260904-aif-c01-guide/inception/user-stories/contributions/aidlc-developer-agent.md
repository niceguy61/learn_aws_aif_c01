## Contribution

### 종합 판단

User Stories 초안은 실행 대상을 애플리케이션이 아닌 정적 UTF-8 Markdown/CSV로 제한하고 있어 구현 가능성이 높다. 계정, 답안·진도 저장, 유료 AWS 실습, 프로덕션 시스템 구축을 요구하는 acceptance criteria는 발견되지 않았다. 다만 실제 집필·추적성 작업으로 옮길 때 막힐 수 있는 경계가 몇 가지 있으므로, Delivery Planning에서 작업 단위와 선행 산출물을 명시해야 한다.

### 스토리 크기와 구현 단위

- **US1.1**은 시작 안내·공식 범위·학습 지도에 한정되어 적절한 크기다. 단, AC1.1.3의 “항목을 선택하면 이동”은 애플리케이션 상호작용으로 해석될 수 있다. 정적 구현에서는 “항목의 Markdown 링크를 따라 관련 문서·문항·복습 자료로 이동”으로 해석을 고정해야 한다.
- **US1.2**는 상대 일정과 정적 체크리스트로 구현 가능하며 적절한 크기다. 완료 상태를 자동 저장하거나 계산하는 기능으로 확장하면 안 된다.
- **US2.1**은 D1~D5의 모든 도메인 문서와 각 README를 포함하므로 사용자 가치로는 타당하지만, 단일 구현 작업으로는 너무 크다. Delivery Planning에서 D1, D2, D3, D4, D5를 각각 문서 작성 단위로 나누고, 도메인 README·개념 문서·용어 연결·문서 검증을 각 단위의 완료 조건으로 배치하는 것을 권장한다. 이는 사용자 스토리를 변경하지 않고 구현 단위만 분해하는 방식이다.
- **US3.1**은 정적 시나리오 문항과 해설 묶음으로 구현 가능하다. 문항 필드가 이미 정의되어 있으므로 도메인별 또는 기준선 행별 파일 분할을 Delivery Planning에서 정해야 한다.
- **US4.1**은 카드, 용어 퀴즈, glossary, Anki CSV라는 서로 다른 정적 형식을 포함한다. 하나의 사용자 가치로 유지할 수 있지만, 생성·검증 단위는 `glossary`, `cards`, `term-quiz`, `anki-csv`로 분리해야 누락과 인코딩 오류를 추적하기 쉽다.
- **US4.2**는 100문항 이상이라는 수량과 전 기준선 행 커버리지를 동시에 요구하므로 가장 큰 스토리다. D1~D5 또는 기준선 행 묶음별 문항 파일로 분할하고, 각 묶음을 독립적으로 검증한 뒤 전체 인덱스로 합치는 작업 구조가 필요하다. 공식 기준선 행 수가 100개를 넘으면 “100문항 이상”은 하한일 뿐이며 행별 최소 1문항 규칙이 우선한다는 점을 구현 계획에 명시해야 한다.
- **US5.1**은 독립적인 사용자 기능이라기보다 모든 문서·문항·복습 자료에 걸친 품질 제약이다. 정적 구현에서는 품질 검사 체크리스트와 판정 기록을 산출물로 정의하고, 별도의 자동 최신성 서비스나 콘텐츠 관리 애플리케이션으로 확대하지 않아야 한다.

### 정적 Markdown/CSV 구현 가능성

- 문서 간 이동은 상대 Markdown 링크와 도메인 README의 읽기 순서로 충분하다. “열기”, “선택”, “확인” 같은 표현은 런타임 UI가 아니라 파일 열람·링크 이동으로 정의해야 한다.
- 문항은 Markdown 또는 승인된 UTF-8 CSV로 저장할 수 있다. 문항마다 고유 `question_id`, 기준선 ID, 도메인, 정답, 해설, 출처 URL, 난이도, 범위 분류를 유지하면 정적 파일만으로 AC4.2.2를 충족할 수 있다.
- Anki 자료는 헤더와 필드 인용 규칙을 명시한 UTF-8 CSV로 제공하면 된다. 쉼표·줄바꿈·큰따옴표가 포함된 해설을 CSV 규칙에 맞게 인용하고, 가져오기 안내에서 구분자와 인코딩을 설명해야 한다. 학습자 답안이나 가져오기 결과를 저장할 필요는 없다.
- 정적 점수 워크시트는 수기 입력 칸과 산식 설명만 제공한다. 자동 점수 계산, 브라우저 저장소, 계정, 서버, 데이터베이스를 acceptance criteria에 추가하지 않는다.
- 내부 검증을 위해 JSON/YAML 추적표나 간단한 검사 도구를 사용할 수 있지만, 그것은 작성·검증 산출물이며 사용자용 실행 애플리케이션이나 학습자 데이터 저장 기능이 아니다.

### D1→D5 의존성 및 권장 순서

현재 D1→D5 작성 순서는 요구사항과 일치한다. 그러나 실제 선행 관계는 다음처럼 명시하는 것이 안전하다.

1. AIF-C01 공식 시험 안내서의 revision, 도메인, 비율, 작업·기술 행을 먼저 확인하고 `AIF-C01-D<n>-T<n>` 기준선 목록을 확정한다.
2. 공식 사이드바 인덱스와 source registry를 작성하고 URL·제목·확인일·접근 상태를 기록한다.
3. D1 문서와 D1 README를 작성하면서 문서 ID, 용어, 기준선 매핑을 만든다.
4. D1의 카드·퀴즈·Anki·문항을 생성하고 역방향 매핑을 검증한다.
5. 같은 절차를 D2, D3, D4, D5 순서로 반복한다.
6. 모든 도메인 자료가 축적된 뒤 통합 glossary, 4주 경로, 전체 문제은행 인덱스, 점수 워크시트를 통합 검토한다. 4주 경로의 초안은 앞 단계에서 만들 수 있지만, 최종 링크는 실제 문서가 생성된 후 확인해야 한다.

특히 1번이 완료되기 전에 D1 문서나 문항을 `verified`로 표시하면 안정 ID와 공식 범위가 추후 바뀌는 문제가 생긴다. 기준선 미확정 상태에서는 관련 자료를 `draft` 또는 `확인 필요`로 유지해야 한다.

### 안정 ID와 추적성 실현성

추적성은 정적 파일로도 충분히 실현 가능하지만, 양방향 연결 규칙을 구현 계획에서 필드 수준으로 고정해야 한다.

- 요구사항과 사용자 스토리: `FR*`, `NFR*`, `US*`, `AC*` ID를 기존 값 그대로 유지한다.
- 공식 기준선: `AIF-C01-D<n>-T<n>`를 공식 안내서의 실제 작업·기술 행 순서에만 부여하고, 설명·파일 이동 때문에 재번호화하지 않는다.
- 학습 문서: 문서별 안정적인 `document_id`를 front matter 또는 문서 인덱스에 둔다.
- 문항·카드·퀴즈·Anki: 각 항목의 안정 ID와 `baseline_ids` 또는 `source_document_ids`를 둔다.
- 기준선 레코드에는 `learning_document_ids`와 `question_ids`를 최소 필수로 두고, 파생 자료 ID를 추가한다. 반대로 각 문서·문항·카드·퀴즈·Anki 항목에서도 기준선 ID 또는 명시적인 `실무 확장` 근거를 기록한다.
- `blocked` 또는 `확인 필요` 기준선은 매핑이 있더라도 `verified`로 승격하지 않으며, 보류 사유와 영향받는 항목을 기록한다.
- `traceability.json`은 단계별 상위·하위 ID와 상태를 담는 검증 산출물로 사용하고, 사람이 읽는 `outline.md`·source registry와 중복되는 정보를 임의로 수동 복제하지 않도록 단일 원천을 정해야 한다.

현재 stories.md의 예비 매핑은 이 원칙을 대체로 반영한다. 다만 “관련 학습 문서·문제·복습 자료로 이동”은 링크 존재만으로 완료 처리하지 말고, 기준선 행에서 대상 ID가 실제 파일에 존재하는지와 대상 파일에서 기준선 ID를 되돌아갈 수 있는지를 모두 검사해야 한다.

### 범위 경계와 부적합 요구 여부

다음 항목은 현재 정적 범위 안에서 구현 가능하다.

- 문서·README·glossary·카드·퀴즈·Anki CSV·문제은행·점수 워크시트
- 공식 출처 URL, 제목, 확인일, 접근 상태, 시험 범위/실무 확장 표지
- D1~D5 읽기 순서와 상대 4주 체크리스트
- 문항별 정답·오답 해설 및 기준선 추적
- 초보자·개념 단위·민감정보·링크·제목 검사의 판정 기록

다음으로 해석되거나 확장되어서는 안 된다.

- AC1.1.3의 “선택”을 웹 애플리케이션의 라우팅·검색·상태 관리로 구현하는 것
- AC1.2.3의 완료 체크를 사용자별 저장 기능으로 구현하는 것
- AC4.2.3~AC4.2.5의 점수 산식을 온라인 자동 채점·계정·답안 수집으로 구현하는 것
- AC5.1.1~AC5.1.4의 출처·품질 확인을 자동 최신성 모니터링, 유료 AWS 호출, 또는 외부 저장소로 구현하는 것
- 서비스 시나리오를 실제 AWS 계정, 배포된 AI 솔루션, API, 데이터베이스, 인프라로 검증하는 것

### 구체적 권고

1. Delivery Planning에 `baseline registration`을 모든 D1 작업의 선행 산출물로 선언한다.
2. US2.1과 US4.2를 각각 D1~D5 도메인 묶음 또는 기준선 행 묶음의 구현 단위로 분해하고, 각 단위에 생성·역방향 추적·링크·초보자 검토 완료 조건을 둔다.
3. AC1.1.3의 정적 구현 해석을 “Markdown 링크 이동”으로 명시한다.
4. 문서·문항·카드·퀴즈·Anki의 ID 필드명과 허용 상태값을 단일 메타데이터 규약으로 고정한다.
5. 100문항 목표와 기준선 행별 최소 1문항 규칙의 우선순위를 수량 계산 예시와 함께 delivery 문서에 기록한다.
6. 품질 검사는 자동화된 서비스가 아니라 정적 검사 기록으로 정의하고, 검사 대상 파일·검사일·판정·근거·수정 조치를 남긴다.
7. 각 도메인 완료 시점에 링크·CSV 파싱·ID 중복·고아 매핑·범위 표지 검사를 수행하여 통합 단계의 대규모 재작업을 줄인다.

## Positions

- **스토리 크기:** US1.1·US1.2는 적절하다. US2.1·US4.2는 사용자 가치 스토리로 유지할 수 있으나 구현 단위로는 반드시 도메인/기준선 묶음으로 분할해야 한다.
- **정적 구현 가능성:** 모든 핵심 acceptance criteria는 Markdown/CSV와 검증 기록으로 충족 가능하다. 동작하는 학습 애플리케이션은 필요하지 않다.
- **D1→D5 순서:** 공식 기준선·출처 등록 후 D1부터 D5까지 순차 작성하는 의존성이 구현 가능하며, 공통 glossary·통합 문제은행은 후속 통합 단계가 적합하다.
- **안정 ID·추적성:** 현재 ID 체계는 실행 가능하다. 기준선 행의 문서/문항 최소 매핑과 각 파생 자료의 역방향 매핑을 기계적으로 검사할 수 있는 필드 규약이 필요하다.
- **범위 이탈:** 현재 코드, 유료 AWS, 사용자 데이터 저장, 프로덕션 시스템 요구는 없다. 단, “선택”, “확인”, “점수 기록”을 UI·서버 기능으로 확대하지 않는 해석을 명시해야 한다.
- **권고 상태:** `조건부 구현 가능` — 기준선 등록 선행, 대형 스토리의 구현 단위 분해, 정적 링크·메타데이터 해석을 Delivery Planning에서 확정하면 진행 가능하다.
